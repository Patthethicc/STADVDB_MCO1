ABSTRACT
This paper covers the technical report for the Online Transaction Processing (OLTP) application built for testing concurrency control and global crash recovery of databases. It highlights the design, implementation, and analysis of a three-node homogenous distributed database system utilizing a Master-Slave architecture. In addition to that, the databases were partitioned horizontally, sharding by birth year of the Users table. A custom middleware layer was developed to ensure location and fragmentation transparency, routing transactions dynamically while enforcing concurrency control and data consistency.

The study evaluates the system's performance under four distinct isolation levels (Read Uncommitted, Read Committed, Repeatable Read, and Serializable) and analyzes the efficacy of recovery strategies during global failures. Performance stress testing indicates that Read Committed, when paired with explicit pessimistic locking, offers the optimal balance between transaction throughput and data integrity. Furthermore, the implementation demonstrates robust fault tolerance through automated slave promotion, heartbeat monitoring, and immediate database modification semantics, ensuring the preservation of ACID properties during node crashes and network partitions.

Introduction

Distributed database systems have become a crucial and essential part of modern systems where scalability and high availability are prioritised. While a centralized database would store all of their data in one location, distributed databases store and manage their data in multiple locations or nodes allowing for better tolerance for shutdowns since one node failing doesn’t instantly cause the system to fail.  

In this project, a distributed database was designed and implemented across three nodes, each responsible for storing specific subsets or replicas of the Users table. Node 1 serves as the central node containing the full dataset, while Node 2 and Node 3 hold vertical fragments categorized by year of birth (2006 and 2007), along with a full replica node for redundancy. This design simulates real-world distributed systems where data is partitioned for efficiency and replicated for reliability. A custom web application backend manages all interactions across these distributed nodes. It determines the correct node to query based on user attributes, forwards write operations to appropriate fragments, and ensures consistency through a combination of replication logic and failure-recovery mechanisms. The backend also exposes REST API endpoints used by a Java-based test script to simulate concurrent user operations and global failures. This project also aims to analyze how the distributed database system acts under different isolation levels and how it responds to global failures.

Distributed Database Design

The system developed encompasses a 3-node homogenous distributed database, utilizing master-slave database system architecture. Encompassing one central node and two horizontally fragmented nodes, the system supports concurrent transactions, isolation-level specificity, replication, and recovery. For the scope of this project, only the “Users” table was utilized, following a homogenous schema across all three nodes. Horizontal fragmentation was done by the user’s dateOfBirth year, with SLAVE 06 and SLAVE 07 getting rows with 2006 and 2007 respectively.

Figure 1.0 Diagram of Distributed Database Structure

The ‘MASTER’ central node inherits a full copy of the Users table, being the main entry point and receiver of all transaction-related INSERT / UPDATE / DELETE database operations. The two read-replica horizontal fragment nodes, “SLAVE 06” and “SLAVE 07” each contain fragments of the original “Users” table, each inheriting rows with the dateOfBirth years 2006 and 2007 respectively. In implementation, the permissions for each node are enforced through ‘getReadPool’ and ‘getWritePool’, giving the MASTER node authoritative read-write-access to the database and the fellow fragment nodes, while SLAVE 06 and SLAVE 07 have read-only access.  Fragmentation is enforced by only allowing years of 2006 and 2007 for their respective nodes, while replication happens primarily within the MASTER node. For replication, the MASTER node enforces a synchronous WRITE on the fragment nodes per transaction, updating the fragment nodes through the central node’s write authority. 

CRUD is done via REST API: INSERT for rows with validated DOB into MASTER, UPDATE with isolation levels via SET SESSION TRANSACTION ISOLATION LEVEL, DELETE via user id, and READ via read-all, id, and year. Concurrency is also implemented with beginTransaction(), commit(), and rollback(). The update mechanisms use explicit DB operations on the master connection, having getConnection(), begin(), execute(), and commit(). The function updateUserById() sets the isolation level before beginning the transaction. 

Failure and recovery handling is done through automated slave promotion, periodic health checks, and transactional rollback/commit semantics to preserve correctness during and after failures. 



Figure 1.1 Diagram of promoteSlave() cycle

Initially, connect.js polls nodes every 10 seconds to detect the availability of the central node. Once the master is detected to be down, the changeMasterNode() functionality runs, selecting any available slave node as replacement, and promotes it through promoteSlave(). promoteSlave() contains SQL commands to convert the slave into a MASTER with STOP SLAVE, SET PERSIST, among others. The remaining node has its master reassigned via CHANGE MASTER TO so that they replicate from the newly appointed MASTER. Once the old master node is detected to be back online, recoverOldMaster() is called, reconverting all other nodes back into slaves and resyncing them to the old master node.

The system uses writes for master transactions (beginTransaction → execute → commit). However, if a connection crashes during a write, the catch block rolls back the master transaction to avoid any partial states, allowing the operation to be retried or continued so that the DB retains a consistent state. If a promotion occurs while writes are mid-operation, the promoted slave continues accepting writes, while the system relies on transaction rollback semantics to avoid inconsistencies. 

Concurrency Control and Consistency

In the developed web application, the central locking strategy operates in the master-slave mode. Focusing all writing (Creating, Updating, and Deleting) in the Master Node (Node 2) streamlines the system and avoids the intricacies of dispersed deadlocks seen in multi-master scenarios. Within the application, _updateUserById_, and deleteUserById_ functions, pessimistic locking is employed in the SQL query as SELECT … FOR UPDATE. When concurrent transactions attempt to access the same record, ($T_1$) in one transaction, the system ensures that it exclusively locks the record to prevent any other access or modification. While the other concurrent transaction ($T_2$) is made to wait until $T_1$ makes a commit or a roll back to ensure the database properties (ACID) are kept. 

Update Strategy & Architecture

The architecture uses a Master-Slave with Horizontal Fragmentation. The code specifically designs the nodes with roles where Node 2 is the MASTER, and Node 1 (SLAVE 2006) and Node 3 (SLAVE 2007) are read-only replicas/fragments. This structure enhances the system’s efficiency in handling read-dominant workloads (which is the average case for web applications), with SELECT queries sent to slave nodes and a central consistency controller for all INSERT/UPDATE operations at the Master.

Database Consistency Mechanism 

The update strategy employed is Primary Copy with Asynchronous Replication:
Write Path: The application middleware (users.services.js) routes all state-changing operations to the getWritePool() (Master Node).
Read Path: Queries are routed to getReadPool() (Slave Nodes), which contain horizontally fragmented data based on the dateOfBirth year (2006 vs. 2007).
Consistency Logic: The code initially attempted a "Dual Write" strategy (writing to Master and Fragment synchronously), but these lines are commented out in the final implementation. Therefore, the active strategy relies on the Master Node to serve as the "Source of Truth." Consistency is guaranteed at the Master immediately upon commit.

Isolation Level
Taking into consideration the structure of the code as well as the updateUserById function, the best isolation level for this application should be READ COMMITTED with the use of explicit row locking (FOR UPDATE). Although SERIALIZABLE gives the best protection, the negative impact on throughput is concerning. The code sample enforces serialization on certain rows with the use of FOR UPDATE. This gives the database the power to operate on a lower global isolation level (READ COMMITTED) to encourage concurrency on rows with no contention, while the code avoids the problems of “Lost Updates” and “Write Skew” on the particular rows focused on. Using the code sample: await connPrimary.query(SET SESSION TRANSACTION ISOLATION LEVEL ${isolation}``); gives the user the ability to change the strategy dynamically, but the code sample makes it clear that the focus is on FOR UPDATE, which suggests row-level locking as the primary consistency guardrail
Data Transparency
	The middleware’s service-layer design allows for impressive location and fragmentation transparency. Applications can never know the details of the physical network topology or the locations of the actual data since every detail of the distributed system is abstracted out. Consider the case of getAllUsers. It runs parallel queries on two nodes, SLAVE 2006 and SLAVE 2007, and, after retrieving the intermediate results, merges them, before sending them to the user. The user sees one table, one of the results from the API, but the data comes from different databases from several subnetworks. The system is fragmentation transparent as well. The data is horizontally tagged (sharded) by dateOfBirth and each query is routed based on which dateOfBirth range it belongs to, and getAllUsersByDate, which routes the queries for 2006 to Node 1, 2007 to Node 3. The client is insulated from concerns over data location, and the data will remain unpartitioned for them. Most importantly, the middleware is where all the sharding logic compute resides. If the rules and node allocations for sharding are updated, the only thing that needs to change is the service layer, and nothing will be required from the client.

Global Failure and Recovery

There is a need for recovery strategies when it comes to distributed database systems to prevent further damage from happening when crashes or attacks occur during transactional processes or when the database itself is idle. These strategies will also promote data consistency, fault tolerance, system reliability, atomicity of transactions, and durability which promotes data integrity and consistency and continuous system operability while preventing data loss and corruption.

Implemented systems/strategies

Inside a recovery operation, frequent checks within the three databases are done to determine if one of these has crashed. This is specifically important for checking if the master node has crashed as this node is the only one that can do WRITE functions such as UPDATE and DELETE. It also looks out for transactions that are happening concurrently when a crash suddenly takes place as it ensures that the transactions are properly done without any inconsistencies and irregularities when the transaction happens again. With this concept in mind, the group implemented a Master-Slave Recovery System when the Master node crashes, a Slave is promoted and an immediate database modification where if the connection crashes or gets interrupted, the transaction will commit the proper values needed.

Insights and Strategies
The results of the project show how the distributed database handles the concurrent transactions, replication and recovery. The central node acts as the primary writer to the other fragment nodes. The update logic in users.services.js ensures that writes are executed on the master node using explicit transactions, row-level locks, and isolation-level enforcement. Reads are allowed on all nodes, and replication ensures that committed updates eventually reach the central node. These mechanisms allow clients to interact with the system as if it were a single unified database, even though the underlying data is fragmented across shards.

Importance of Distributed Databases

Distributed database systems are crucial for modern applications requiring high scalability and high availability. The distributed systems avoid the single point of failure and bottleneck of the centralised architecture by partitioning the data and processing across multiple nodes. The systems illustrate distributed systems core tenants, such as improved fault tolerance and the ability to manage traffic volumes that exceed single server systems, as they continue to operate regardless of the failure of one or some nodes. This is in line with the principles established by Stonebraker and others, who state that distribution is the solution to the problem of large scale transactional workload.

The decision to pair READ COMMITTED with explicit Pessimistic Locking (SELECT ... FOR UPDATE) is critical. This approach maximizes throughput by allowing high concurrency for non-conflicting reads and writes, while explicitly enforcing serialization only on the specific data items being modified. This pragmatic strategy prevents critical anomalies like Lost Updates and Write Skew without imposing the severe performance penalty of global Serializable isolation, confirming practices reported in modern DBMS tuning guides (Gray, J., & Reuter, A., 1993).

Data Fragmentation
	The database was sharded by dateOfBirth year, and replicated via a Master-Slave setup which are necessary aspects to overall performance and reliability. Fragmentation enhances the performance by directing queries to smaller, more relevant datasets, thereby reducing I/O and query latency. Replication ensures high availability and fast read performance by duplicating data across multiple nodes. The Primary Copy with Asynchronous Replication update strategy dictates that consistency is immediately enforced at the Master node through centralized locking. The resulting consistency in Slave nodes is eventual consistency. While this improves write speed by not requiring synchronous commits across all nodes, it means the Slave nodes may briefly return stale data, a known trade-off inherent in Master-Slave configurations (Gilbert, S. &  Lynch, N., 2002).

Data Replication Benefits During Node Failure
Data replication provides immediate benefits to users even when a node fails. If one of the read-replica nodes (SLAVE 06 or SLAVE 07) were to fail, the application could potentially failover to the Master node (Node 2) for reads, or the query logic could be temporarily disabled for the failed fragment. Crucially, the Master Node maintains the full copy of the data, ensuring the application can continue processing all write transactions and most read transactions, providing continuous system operability and preventing the system from entirely crashing.

Conclusion
	This paper highlights an in-depth overview of an implemented 3-node homogenous master-slave distributed database for the Users table, with a Node.js that routes READs to fragments and sends all WRITEs to MASTER. Implemented features span concurrent updates, CRUD, failure-recovery strategies, master promotion, isolation control, transaction management, immediate database modification semantics to prevent partial commits, as well as horizontal fragmentation on the birth year, with SLAVE 06 getting rows containing ‘2006’ and SLAVE 07 containing ‘2007’ entries.  
This entailed implementing read-write permissions and isolation control amongst different facets of the project, primarily through how transactions are handled to both synchronize the entire database and enact commit-consistent CRUD operations on the master node. Aside from this, the master-slave model was utilized to illustrate and determine the failure-recovery process, through the use of appointing new masters, rerouting directed node updates to the new master node, and checking for the old master node to refactor the entire system back to its initial 3-node state post-recovery through synchronous replication, via REST API. 
The testing has also shown that while the difference in performance between the isolation levels for concurrency is little, the gap between read committed over the other isolation levels is still present. The speed in performance is only beaten by read uncommitted, and its security is also still present, not accepting anything uncommitted. For global failure recovery, both types of test cases focus on different types of nodes failing and the other surviving nodes still committing writes to it. After the testing, although there are some issues with the recoveryCentral() function, the test cases still work and succeed.
Overall, the implemented project highlights the versatility of distributed databases with respect to simulating and handling failure cases, most especially with regards to retaining data integrity amongst system crashes.
